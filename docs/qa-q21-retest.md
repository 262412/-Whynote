## Q-22/P2：数据库等待使菜单提前过期（Q-11 回归）

来源：PR #22 自动评审提出风险，本 QA 用实际 SQLite 锁等待独立复现后登记，未把评论直接当缺陷。

操作：新虚构 SQLite 上另一连接持有 BEGIN IMMEDIATE 0.75 秒；实际 Action/EventStore 等待锁释放后预约菜单。用户等待由 Action 局部时钟受控推进 59.5 秒，返回本菜单有效签名。分别使用显式 UUID 与旧无 ID 请求；仅宿主 fixture 查询、菜单回调与用户计时受控，数据库连接、事务及锁是真实执行。

预期：菜单获得完整 60 秒响应时间；59.5 秒提交成功，产生动作→展示→选择。真正 60.1 秒应拒绝，不追加展示/选择。

实际：锁等待约 0.8 秒，加菜单内 59.5 秒，被判 ticket_expired；两条路径均仅保留 negative_feedback_action_recorded。无锁条件下 59.5 秒成功；锁等待后真正 60.1 秒均拒绝。精确等待和事件序列见摘要，受控用户等待不是实际浏览器耗时。

原因：Action 在 begin_host_click/create_action 及票据预约之前计算 issued_at/now/expires_at，但菜单回调仍独立 wait_for 60 秒，提交检查把预约等待计入用户响应期限。Q-21 重排了旧兼容路径的时钟位置，也触发同一回归。受影响 FR-11/13、D-15、Q-11。

修复后复验条件：保持动作/Outbox/点击/票据的事务与并发顺序，同时从明确的菜单可响应时点保证期限；验证锁等待、小数边界、真超时、进行中重试状态与期限一致、旧回调零追加、新菜单不被重试替代。不能删断言或缩短用户承诺规避。
