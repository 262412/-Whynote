# 知因・Whynote 开发规约

状态：2026-09-25 生效；2026-09-27 更新第 1.1 节文档与代码双向维护规则、第 3 节 Git 交付与分支清理规则。适用于本仓库的代码、事件契约、模型适配、评测和发布变更；不代表 PRD 或上线审批已完成。产品名以本项目约定的「知因・Whynote」为准。

## 1. 产品方向与证据等级

- 当前定位是**可审计的负反馈信号闭环研究 PoC**：先可靠记录点踩，再验证原因辅助标注能否提高有用反馈产出且不增加不可接受的用户成本。不能以 Jev 可调用、测试通过或推测数量增长替代产品价值验证。
- 需求行为以[《JEV 产品 PRD》](https://my.feishu.cn/wiki/XG6SwutL0i3fyWkwmhScEEB86Gg)经评审的版本为准；[技术开发文档](https://my.feishu.cn/wiki/GuphweJs3iWwBRkBDjlcljA16bh)定义实现建议。2026-09-25 历史读取版本分别为 66 和 8；当前实施路线按D-21及[项目说明](../README.md)执行。未签署的阈值、权限、排期、预算和模型质量均标为「待决策」，不得写成已批准事实。
- 每个需求在 PR/任务中写明 FR、TD 或决策编号、用户场景、成功指标、边界条件和验收证据。需求冲突先在决策记录中写明选项、影响、责任人和结论；不得让代码隐式决定产品语义。
- 当前产品假设优先用常规原因菜单作对照；模型建议、自动附加、自用训练数据均要分别证明价值、来源正确性和风险可控。模型推测永远不等于用户确认。

### 1.1 PRD、技术文档与代码的双向维护

- 框架、功能与使用说明优先维护项目和宿主两个简洁 README；仅确有必要的规约、合规/来源及脚本依赖另留文件。逐提交报告、回执、比较和进度写在对话或 PR，不新增重复 Markdown。完整契约与历史失败可由固定 Git 提交恢复，不能因精简文档把未签署结果写成完整验收。

- 更新飞书前读取当前修订，按原章节和需求/字段/API 条目局部修改；没有合适归属的内容才新建有明确主题的区域。不得把每轮进展、决定或验收结果逐条堆到文末，代替正文更新。
- 从文档逐项查实际代码入口、调用路径、字段读写、事件/存储和用例；从代码反查新增或变化的行为是否已回填 PRD 与技术契约。固定核对提交，区分主干、未合并 PR、未提交工作及实际部署版本，不能混作“当前实现”。
- `✔` 只放在原功能、字段或契约条目中，紧邻已实际实现的具体子项，并列出日期、代码版本、位置、验证来源与剩余缺口。部分实现拆分标记；设计、建议、审批决定、测试计划不打实现勾。只有定义、枚举、测试 fixture 或未接入的纯函数时，只能标记该有限范围，不能推定完整功能已落地。
- 实现状态、开发复测、独立验证、完整 FR 验收和发布批准分别维护。代码已实现但仍有边界缺陷时，就地注明受影响行为；不得用一个勾遮盖失败，也不得因尚未完整验收而把已有实现全部写成“未实现”。
- 历史复测和旧失败集中归入文档的历史区域，保留日期、版本、原结论与证据；历史标记不充当当前完成清单。当前决定回填决策表，当前缺陷回填受影响条目，计划回填实施章节。写后重新读取，核验位置、内容、修订和资源保留；若并发更新改变目标内容，重新比对后再写。

## 2. 设计与代码边界

1. **纵向小切片。**一次 PR 只解决一个可验收的行为或一组紧密相关的缺陷；避免同时修改事件语义、模型策略和 UI。API、业务规则、事件存储、供应商适配各守自己的边界。`api.py` 只负责鉴权/校验/传输，`domain.py` 负责纯规则和状态转换，`store.py` 负责持久化与事务；新组件按明确责任单独建模块。跨层依赖由接口/依赖注入连接，禁止供应商 SDK 进入领域规则。
2. **先定契约再改代码。**任何事件、状态、原因 taxonomy 或对外 API 变更，先列字段含义、合法转换、幂等键范围、版本兼容和旧数据重放结果。事件只追加；`record_id` 标识单条事件，`event_id` 标识一次点踩；动作与 Outbox 同事务写入，HTTP 点踩不等待推断。删改旧事件必须另立迁移方案与审计评审。
3. **失败保持可解释。**授权/场景/采样/预算任一不通过，不读取上下文或调用模型，原因保持空；入样概率不可识别时权重为空。上下文、校准器、模型版本或策略缺失时关闭自动附加并记录原因。不得以静默默认值伪造概率、版本、标签或费用。
4. **来源和撤销分离。**自动附加只可标为 `model_inferred_unconfirmed`；只有明确用户动作可变为 `selected`、`confirmed` 或 `edited`。`action_retracted` 取消点踩及未完成任务，`attribution_invalidated` 只撤销推测；未响应、拒填、跳过和「都不是」定义分别验收。当前投影与历史审计的语义都要写明。
5. **数据最小化。**事件、普通日志、队列和指标标签不放原始问题/回答、密钥或自由文本；只在获准门控后创建白名单、脱敏、加密且有到期/删除规则的快照引用。未获数据流和供应商条款审批前，不向外部模型发送生产上下文。训练和 gold 的取数路径必须排除未确认推测与伪标签。
6. **避免抽象债。**先用最简单的实现完成当前契约；新增依赖、框架、兼容层或通用基类须在 PR 中说明实际使用场景和替代方案。重复逻辑出现且语义一致时再抽取。模块职责混杂或一个改动需跨越多个无关层时，先拆分再扩展。

## 3. Git 交付、评审与分支清理

### 3.1 分支按开发切片管理

- 一个可验收的开发切片使用一个短期分支和一个 PR。同一切片的修复、补测试、评审修改继续使用原分支；不因每次提交、复验或对话创建新分支。只读评审可使用固定提交的 detached checkout，无需新建长期分支。
- 新切片从核实后的最新远端 `main` 建分支，默认使用 `codex/<任务名>`；先检查已有分支、PR、工作树及任务占用，优先复用空闲工作树。依赖尚未合并的 PR 时，明确基线与合并顺序，不能隐式叠加未批准改动。
- 原工作区有未提交改动时，保留现场，在合适的隔离工作树开展工作；不得为了同步基线而覆盖、清理或擅自 stash 用户改动。禁止直接提交到受保护的 `main`。

### 3.2 每个完成的切片都要走到合并收尾

- 标准流程为：**完成改动 → 本地验证 → 提交并推送同一分支 → PR 检查与评审 → 合并 → 核验远端 `main` → 判断并执行分支/工作树清理 → 交付回执**。中间提交可以多次进行，不要求把尚未完成的工作逐次合并。
- 用户要求完成开发交付时，默认包含满足门槛后的推送、合并和安全清理，不在“已提交”“已推送”或“已开 PR”处结束，也不重复请求同一交付范围内的普通合并许可。用户明确要求仅分析、仅改文档、不推送、暂不合并或在独立评审处停止时，以该任务的明确范围为准；本次规约修改不构成对积压 PR 的批量合并或分支批量删除指令。
- 合并前确认 PR 非 draft、目标分支正确、无冲突、最新 head 的必需 CI 通过、阻断评审意见已解决，并至少取得一名非作者的有效批准；事件/隐私/模型质量/费用相关改动再由对应责任人签署。追加提交或解决冲突后重新核对检查和批准是否仍覆盖当前版本，不能引用旧 head 的绿色结果。
- 仓库管理员负责配置 GitHub 分支保护、必需 CI、禁止绕过和过期审批失效；在配置生效前这些仍是团队执行规则。门槛未满足时，交付状态写“待合并/阻塞”，列出具体原因、责任人和下一步；不得绕过检查或把作者自审当成非作者批准。
- PR 描述使用仓库模板：需求/决定编号、改变的用户行为、数据及事件契约、失败和回滚路径、测试证据、未完成项。不要把局部单测通过写成整项 FR 通过。
- 本地和 CI 使用锁文件安装并运行 Ruff lint、Ruff format 检查、pytest。新增行为至少覆盖正常、拒绝/无权限、重试/幂等和相关状态边界；涉及撤销、Outbox 或预算的改动增加竞态/重复投递测试；涉及真实模型的改动增加契约、无效响应、限流/超时和版本失配测试。仅改文档无需新增镜像实现的测试。
- 修复失败由引入改动的 PR 完成。不得为了通过 CI 删除失败用例、降低断言或长期跳过测试；临时隔离必须记录工单、负责人、截止日期和风险。数据库或事件 schema 变更附前向迁移、旧数据读取/重放验证和回滚说明。
- 代码审查关注边界与可维护性：输入是否由可信来源产生、状态转换是否闭合、是否重复保存敏感数据、错误是否可定位、名称是否表达业务含义、逻辑是否能独立测试。风格交给自动工具，评审精力用于业务正确性。
- 合并后记录 PR、合并提交及远端 `main` SHA，确认合并结果已包含交付内容，并检查合并后适用的 CI。出现失败由该切片继续修复或按回滚方案处理；检查仍在运行时标为“已合并，验证待完成”。合并成功不代表完整 FR 验收或发布批准。

### 3.3 合并后必须判断是否删除旧分支

- 每次合并后由交付执行人核查源分支及本任务使用的旧分支；满足下表条件的短期分支默认删除远端和本地引用，不留到下一次无关任务。远端删除与本地删除分别记录结果；远端跟踪引用的 prune 不能替代实际分支清理。

| 分支或工作树状态 | 处理规则 |
|-|-|
| PR 已合并，分支无未交付提交，且无任务、进程、其他 PR 或工作树依赖 | 删除远端短期分支；释放工作树占用后删除本地分支 |
| PR 已合并，但分支又有新增提交或仍被其他工作依赖 | 保留，记录新增工作/依赖、责任人和解除条件；后续新切片优先另从最新 `main` 开始 |
| PR 未合并、检查失败、仍在评审或待独立批准 | 保留并推进原 PR；不得为减少数量直接删除未交付工作 |
| 任务明确放弃，但仍有未合并内容 | 先记录放弃范围并保存可恢复记录；确认内容处置后再清理，不能仅凭长时间未更新判断可删除 |
| `main`、默认分支、发布/维护分支或共享分支 | 不纳入短期分支自动清理 |
| 工作树仍有任务/进程占用或未处理的用户数据 | 保留，先核查占用和数据保存方案；合并本身不证明工作树可以删除 |

- 删除前重新读取远端分支 SHA、PR 合并状态和本地差异，确认当前分支内容已交付且没有合并后的新提交。squash/rebase 合并可能不保留源提交祖先关系，须结合 PR 的已合并 head 和内容差异判断；不能只按分支名、创建时间或 `git branch --merged` 结果删除。删除时若引用已变化，停止并重新核查。
- 优先保留可复用的空闲工作树。确需移除 Codex 托管工作树时，使用应用的工作树归档能力保存可恢复快照；归档前确认无任务或进程依赖，并另行保存需要保留的忽略文件（如 `var/` 下的数据库、日志、审计数据），这些文件不随普通归档保存。不得用 shell 递归删除、`reset --hard`、`git clean` 或强制删除来绕过未处理内容。
- GitHub“合并后自动删除头部分支”可辅助远端清理，但不能替代本地分支、工作树和依赖检查。该设置由仓库管理员核实配置；启用前按本节手动完成清理，不把建议写成已开启。
- 每次交付收尾顺带检查本任务遗留分支；每周研发整理一次其余积压分支，记录分支、关联 PR、责任人、保留原因、清理条件和下次检查日期。没有明确用途的旧分支进入处置清单，不能无限期只记“保留”。

### 3.4 交付回执

- 每个切片的回执列出：需求编号、PR、交付 head、验证证据、评审/签署、合并提交与 `main` 检查结果、远端/本地分支处理、工作树处理、剩余阻塞。清理不适用或暂不能执行时，写明原因和后续责任人。
- “研发交付完成”要求改动已合并、合并结果验证完成、该清理的引用已处理、保留项有明确理由和后续安排。产品完整验收与上线批准仍按第 4 节独立判定。

## 4. 按风险分层的验收门槛

| 阶段 | 必须提供的证据 | 不满足时的动作 |
|-|-|-|
| 基础切片 | 对应 FR 的端到端用例、事件重放、租户隔离、幂等与拒绝路径；版本/来源字段可追溯 | 保持该 FR 为部分实现；不接生产上下文 |
| 离线自动探索（D-21） | 来源/固定文件/使用范围、真实映射及反馈隔离、预算/失败对账、本机运行保护和可读报告；无标签指标为NA | 不要求人工标签、48小时复标、固定30/60/180或正式冻结才能运行；结果仅作诊断，不能宣称质量通过或开启生产 |
| 正式离线质量验收 | 冻结 taxonomy 与双人裁决 gold；同一隔离集比较规则、本地模型和 Jev；报告中文、partial、OOD 切片的 Macro-F1、逐类误判、Brier/ECE、risk-coverage 及置信区间 | 仅研究；不进入 shadow |
| Shadow | 真实准入/快照授权、预算预占释放、Outbox 消费、熔断与回滚演练、来源分层及审计通过；不改变用户可见原因 | 保持常规原因路径 |
| 用户确认试点 | 常规原因对照、1–3 候选与「都不是」体验评测；预注册主指标、护栏、实验单位和停止条件 | 不扩大流量 |
| 受控自动附加 | 独立校准器与模型/类别/场景/feature_set 兼容；产品、算法、安全、隐私审批；系统推测标识和更正入口；分片开关、监控和值班回滚 | 默认关闭或立即回退 |

正式质量与用户效用实验的数值阈值、样本量、SLO 和观察窗由责任人在实验**开始前**签署，不能用事后挑选的结果补定义。Useful Feedback Yield、动作成功、用户耗时、确认/更正/撤销、来源混淆、校准、成本及隐私风险分开看；仅在可识别入样概率且满足 positivity 时作 IPS 结论。完整验收须有实际证据位置、运行日期、版本和签署人。

## 5. 持续监控与方向调整

- 工作日检查飞书两份文档修订、GitHub `main`/PR 与 CI、[质量基线](quality-baseline.md)中的阻断项。文档变更先比对需求编号和影响，再更新本仓库决策/基线，不把未评审草案自动视为新发布许可。
- 每周评审一次「问题是否真实」：点踩量、现行原因填写率/耗时、内部处理价值、用户访谈、费用和隐私限制。若证据不足，继续做埋点与常规原因基线；若模型无增益，优先改原因定义/交互或停止模型路线；若中文或 partial 切片退化，收窄适用场景并提高确认/拒识比例；若来源或权限失守，暂停推断和训练导出。
- 监控发现阻断缺陷时标记 NO-GO，列明受影响 FR、复现证据、负责人、下一次复验条件。方向调整以书面决策记录体现：旧假设、证据、新范围、放弃项、指标与回滚。用户可见行为的变更须同步 PRD、技术契约、测试和运营说明。
